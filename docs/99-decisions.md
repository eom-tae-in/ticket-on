# 99. 확인 과제 · 만들지 않기로 한 것 · 확정 숫자 · 뒤집힌 결정

기획 회의에서 **모든 안건이 닫혔습니다.** 여기 남은 것은 네 종류입니다.

**단계를 나누지 않습니다.** "MVP"나 "2단계로 미룬 것"은 없습니다. 만들기로 한 것은 전부 만들고, 만들지 않기로 한 것은 아래 B에 이유와 함께 적혀 있습니다.

## A. 확인 과제 — 우리가 정할 수 없는 것

## B. 만들지 않기로 한 것

**없는 것에도 결정이 있습니다.** 되돌아오지 않도록 이유와 함께 기록합니다.

| 항목 | 이유 |
|---|---|
| **퇴장 스캔 / 체류 인원 관리** | 입구에 줄이 생기고 실패율이 높음. 회차로 시간대를 나누는 것과 입장 누계로 간접 대응 |
| **오프라인 검표** | 기기 분실 시 그 자체가 개인정보 유출. 기기 간 동기화가 안 돼 중복 입장을 못 막음 |
| **추첨 예매** | 예매 흐름을 한 벌 더 만드는 일. 지정석과 궁합이 나쁨 (`06` 참조) |
| **지정석 묶음권 / 다회차 할인** | 날짜 수만큼 좌석을 동시에 선점해야 함. **수량형 묶음권은 회차형에서도 됨** (`05` 참조) |
| **휴대폰 본인확인 (PASS)** | 본인확인기관 계약이 필요해 테스트 결제 환경과 맞지 않음. 그래서 연령·매수 제한·통계는 자기 신고 기반 (`01` 참조) |
| **티켓 양도** | 캡처로 사실상 가능. 공식 기능은 암표를 쉽게 만듦 (`07` 참조) |
| **리뷰·후기** | 소규모 행사는 리뷰 0개가 대부분. 의미가 있으려면 행사가 아니라 주최자에 쌓여야 하는데 그 규모가 안 됨 |
| **웹 푸시** | 허용률 10~20%, iOS 제약, 가입 직후 권한 팝업은 이탈 요인 (`12` 참조) |
| **판매율순 · 최근 판매량 정렬** | 공연일순·최신순으로 충분 |
| **지역 필터** | 행사 수가 적어 대부분 빈 화면이 나옴 |
| **전화번호 문자 인증** | 건마다 비용이 듦. 대신 "관객은 본인 번호를 적는다"를 전제로 두고 번호 중복만 확인 (`01` 참조) |
| **전매 의심 표 강제 취소** | 공유와 전매를 구분할 수 없고, 취소할 즈음엔 이미 팔려 돈을 낸 구매자가 현장에서 막힘. 매수 제한과 이용 정지로 애초에 많이 못 사게 함 (`01` 참조) |
| **일부 회차만 장소 변경** | 장소와 도면은 행사에 하나. 그 회차를 취소하고 새 행사로 엶 (`04` 참조) |
| **공연 시작 뒤 도면 교체** | 이미 공연한 회차 표의 좌석 번호가 바뀜. 남은 회차를 취소하고 새 행사로 (`04` 참조) |
| **절반 넘게 공연한 뒤 중단의 보상** | 소비자분쟁해결기준에 기준이 없음. 따로 정하면 다툼만 늘어남 (`08` 참조) |
| **관리자가 사정을 듣고 정하는 환불 금액** | 모든 문의가 협상이 됨. 관리자 대신 취소는 오류 구제만, 금액은 규정대로 (`08` 참조) |
| **검표 계정의 [티켓 없이 입장 처리]** | 아르바이트생이 판단하게 됨. 운영진 로그인에만 둠 (`10` 참조) |

| **관리자 프로필** | 남이 관리자를 볼 일이 없음 |
| **운영진 프로필 공개 여부 선택** | 실명이 아니라 닉네임이라 개인을 특정하지 않음. 자동 공개로 단순하게 (`01` 참조) |
| **운영진 프로필의 글·연락 기능** | 소통 기능이 되면 메시지함·스팸 처리까지 따라옴. 닉네임·소개·참여 이력까지만 (`01` 참조) |

| **공연 직전 제목 변경 관리자 승인** | 관리자는 제목 변경이 중요한지 판단할 수 없고, 급한 오타도 못 고침. 판매 종료 후 고정 · 이력 · 알림 창으로 충분 (`03` 참조) |

| **관리자 등급 세분화** | 관리자·최고 관리자 2등급으로 충분 (`01` 참조) |
| **운영자의 행사별 권한** | 소규모 단체는 운영진이 모든 행사를 함께 함. "이 행사만 돕는 사람"은 검표 계정이 맡음 (`01` 참조) |
| **소유자 여러 명** | 배상과 정산 계좌의 책임이 흐려짐 (`01` 참조) |
| **회차 취소 시 다른 회차로 자동 이전 · 우선 변경권** | 다른 회차 빈자리는 보장할 수 없고, 우선권을 주려면 다른 회차 판매를 멈추거나 자리를 묶어야 함. 날짜를 옮기려면 연기를 씀 (`04` 참조) |
| **예매자 명단 내려받기** | 인터넷이 끊길 때를 대비하는 대가로 수백 명의 개인정보가 파일로 나감. 파일이 나간 뒤 통제할 방법이 없음 (`10` 참조) |
| **예매자 명단 화면 (주최자 포함)** | 수동 검색에 전화번호 전체를 더하자 명단을 훑어야 할 경우가 사라짐. 주최자용 검색을 따로 둬도 쓸 수 있는 정보가 같아 더 찾을 수 없음 (`10` 참조) |
| **검표에서 예매번호로 찾기** | 폰이 꺼진 관객은 예매번호가 적힌 문자도 볼 수 없음 (`10` 참조) |
| **성별 수집** | 예매에 쓰이지 않아 필수로 받을 수 없고 (개인정보보호법 제16조), 선택으로 받으면 미응답이 섞여 통계가 흐려짐. 연령대 통계로 충분 (`01` 참조) |

전체 교차 점검에서 나온 구멍을 관객 한서윤, 소유자 박정훈, 운영자 이도현 세 사람을 기준으로 닫았습니다.

|---|---|---|

| **회차 시간 잠금** | 행사 시작 1주일 전 → **그 회차 시작 1주일 전, 바꾸면 알림 + 공제 면제** | 첫 공연이 시작되면 마지막 주 회차도 못 고쳤음 (정훈) |

| **가입 동의** | 하나씩 → **"필수 항목 모두 동의" + 마케팅은 따로**. 예매 동의는 하나씩 유지 | 편의는 주되 광고 동의를 묶지 않음 (서윤). 예매 동의는 분쟁 근거 (`01`) |
| **알림함 읽음 표시** | 없음 → **목록 안에서만, 처음 본 순간 읽음, 탭 배지 없음** | 새로 온 것만 구분. 문자로 받은 것까지 쌓이는 숫자는 의미 없음 (`12`) |
| **비밀번호 찾기 안내** | 미정의 → **가입 여부와 상관없이 같은 안내** | 이메일을 넣어 보며 가입자를 알아내는 것 방지 (`01`) |
| **무효 링크 문구** | 취소만 정의 → **취소·변경 / 재발행 / 행사 종료 세 가지** | 받은 사람이 링크가 잘못된 줄 알지 않게 (`07`) |
| **주최자 로고** | 없음 → **선택 업로드, 없으면 첫 글자 + 정해진 색, 관리자 초기화.** 운영진 프로필은 사진 없이 첫 글자 + 색 | 기본 그림은 겹치고 로고로 오해됨. 이름에서 나오는 표시는 구분됨 (`01`) |
| **오늘 판매 수** | 없음 → **예매 현황에 추가** | 공연 기간 폰으로 보는 숫자 (정훈) (`11`) |

### 기술 스택·구조 (2026-10, `16` 참조)

| 항목 | 처음 → 최종 | 이유 |
|---|---|---|
| **서버 형태** | 마이크로서비스 검토 → **모듈형 모놀리스 + 멀티모듈** | 한 동작이 여러 기능에 걸침(예매 → 결제 → 티켓). 1만 명 이하, 1인 개발 |
| **언어** | TypeScript 통일안 → **서버 Java 25(Spring Boot) + 화면 Next.js** | 서버는 헥사고날 멀티모듈을 Spring으로. 화면은 공유 링크 미리보기 때문에 서버 렌더링 |
| **도메인과 DB** | DB를 domain 모듈에 두는 실용안 → **domain은 순수, DB는 infra** | 규칙이 무거워 DB 없이 테스트할 가치가 큼 |
| **DB 접근** | JPA → **jOOQ** | 분리하면 JPA 이점이 사라짐. 좌석 동시성·집계가 SQL에 있음 |
| **들어오는 포트** | 생략 가능 → **둔다** | 처음 쓰는 구조라 경계를 눈에 보이게 |
| **외부 업체** | 지금 선택 → **결제(토스)만 지금. 문자·이메일·파일은 배포 때** | 포트로 분리돼 어댑터만 추가하면 됨 |
