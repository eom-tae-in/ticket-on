# 01. 계정 · 주최자 · 승인 · 약관

## 계정 4종

| 계정 | 만드는 방법 | 할 수 있는 것 |
|---|---|---|
| **사용자** | 자유 가입 | 예매, 변경, 취소, 내 티켓 |
| **주최자 운영진** | 주최자 쪽 로그인을 만든 뒤 **주최자(단체)에 소속** | 소속 주최자의 행사 개설·운영 (권한은 아래 참조) |
| **플랫폼 관리자** | 최고 관리자가 발급 | 주최자 심사·정지, 신고 처리, 행사 페이지 내리기, QR 재발행, 정산 계좌 변경 확인, 마케팅 발송 |
| **검표** | 운영진이 행사별 발급 | 검표 화면만 |

**주최자는 사람이 아니라 단체입니다.** 심사·정지·정산·행사가 전부 주최자에 붙고, 사람은 각자 자기 로그인으로 들어와 소속됩니다. 혼자 활동하는 개인 주최자는 소유자 한 명뿐인 단체입니다.

### 왜 사용자와 주최자를 나눴나

쓰는 기능이 겹치지 않습니다. 배달앱의 손님과 사장님 관계와 같습니다. 승인형을 택했으므로 주최자는 "심사를 통과해 들어오는 존재"인데, 이걸 기존 계정의 부가 권한으로 붙이면 심사·정지·이력 관리가 애매해집니다.

> 회의 중 뒤집힌 결정입니다. 처음에는 "사용자 계정에 주최 권한을 추가로 여는" 안이었습니다.

### 왜 행사는 계정이 아닌가

"행사마다 로그인을 따로 만드는" 안은 폐기했습니다. 행사를 5번 하면 로그인이 5개가 되고, **과거 이력이 흩어져 승인 심사 때 볼 수 없습니다.**

## 주최자와 운영진

GitHub Organization과 같은 구조입니다.

| GitHub | 우리 |
|---|---|
| Organization | **주최자** |
| Owner | **소유자** (1명) |
| Member | **운영자** (여러 명) |
| Repository | 행사 |

**왜 필요한가** — 서비스 대상이 소극장, 대학 공연, 동호회입니다 (`00` 참조). 이런 곳은 여러 명이 함께 운영하고, 동아리는 매년 대표가 바뀝니다. 로그인이 하나뿐이면 비밀번호를 돌려 쓰거나 대표 한 명이 전부 처리해야 합니다.

### 권한 두 가지

| | 소유자 | 운영자 |
|---|---|---|
| 행사 만들기·수정, 초대권, 검표 계정, 현황·통계·정산 보기, 주최자 공개 정보(소개·SNS·로고) 편집 | O | O |
| 판매 중단·재개, 연기·장소 변경 신청 | O | O |
| **행사 취소 · 회차 취소 · 공연 중단 처리** (배상이 걸림) | O | X |
| **출연자 변경 알림 · 공연 지연 처리** (배상·환급이 걸림) | O | X |
| **판매를 시작한 행사의 삭제** (팔린 표·초대권이 없었을 때만) | O | X |
| **정산 계좌** | O | X |
| **운영진 초대·내보내기** | O | X |
| **소유자 넘기기 · 주최자 닫기** | O | X |

**소유자는 1명입니다.** 배상과 정산 계좌가 걸려 있어 책임질 사람이 분명해야 합니다.

**권한은 주최자 단위입니다.** 운영자는 그 주최자의 모든 행사를 다룹니다. 행사별로 권한을 나누지 않습니다. 소규모 단체는 운영진이 모든 행사를 함께 하고, "이 행사만 돕는 사람"은 대부분 현장 스태프라 검표 계정이 맡습니다.

**누가 했는지 남깁니다.** 운영진의 모든 조작에 "누가 언제 무엇을"을 기록합니다. ("초대권 10장 발권 · 운영자 김○○")

### 운영자 초대

```
소유자가 이메일로 초대
  → 받은 사람이 주최자 쪽 로그인을 만들거나 기존 로그인으로 수락
  → 운영자로 소속
```

**운영자는 심사를 받지 않습니다.** 심사는 "이 단체가 믿을 만한가"를 보는 것이고, 단체 안에 누구를 들일지는 소유자가 판단합니다.

**한 사람이 여러 주최자에 소속될 수 있습니다.** 막으면 두 동아리를 돕는 사람이 이메일을 두 개 만들어야 합니다. 주최 관리 화면에 주최자를 바꾸는 메뉴가 생깁니다.

### 소유자 넘기기

대표가 바뀌면 소유자를 넘깁니다. 관리자를 거치지 않습니다.

| 규칙 | |
|---|---|
| 받을 수 있는 사람 | **이미 그 주최자의 운영자인 사람만.** 바깥 사람에게 바로 넘길 수 없음 |
| 알림 | 운영자 전원과 관리자에게 |
| 넘긴 사람 | 운영자로 남음 |

**소유자와 연락이 끊긴 경우** — 전 대표가 졸업하고 연락이 안 되면 넘겨줄 사람이 없습니다. 이때는 운영자가 **관리자에게 이전을 신청**하고, 관리자가 확인한 뒤 소유자를 바꿉니다 (`11` 참조).

### 가로채기를 막는 장치

> 운영자로 들어온 사람이 소유자 자리를 넘겨받고, 정산 계좌를 자기 계좌로 바꾸면 정산금이 그 사람에게 갑니다.

- 소유자는 **기존 운영자에게만** 넘길 수 있습니다
- 소유자가 바뀌면 **운영자 전원과 관리자에게** 알립니다
- **정산 계좌 변경은 관리자가 확인한 뒤 적용**됩니다 (`11` 참조)

### 공개 페이지 — 주최자 페이지와 운영진 프로필

GitHub의 조직 페이지와 사용자 프로필에 해당합니다. **누구나 로그인 없이 봅니다.**

**주최자 페이지**

```
극단 열두달                              ← 닫혔으면 "활동 종료" 배지
소개 · 인스타그램
운영진  조용한고래(소유자) · 푸른바람
──────────────
진행 중   봄 정기공연 「○○」 3/12~3/22
지난 행사 2025 가을 정기공연 · 2025 낭독회 · …
```

| | |
|---|---|
| 들어오는 길 | 행사 상세의 주최자명, 운영진 프로필의 참여한 주최자 |
| 편집 | 소개 · SNS 링크 · 로고는 **운영진 누구나** (선택 입력). 심사용으로 낸 SNS 링크와 별개 |
| 로고 | **선택.** 정사각형으로 잘라 올림 (포스터처럼 크롭 도구). **없으면 이름 첫 글자 + 주최자마다 정해진 색**(8가지 중 하나). 부적절하거나 다른 단체를 흉내 내면 관리자가 초기화 |
| 주최자명 변경 | **소유자가 바로 변경.** 이름 변경 이력(언제, 무엇에서 무엇으로)을 남기고 운영진 전원과 관리자에게 알림 |

**목록에 띄우지 않는 행사**

| 빼는 것 | 이유 |
|---|---|
| 링크 전용 · 암호 보호 행사 | 주최자 페이지에 뜨면 비공개가 깨짐 (`03`) |
| 작성 중 · 삭제된 행사 | 없는 행사 |
| 관리자가 내린 행사 | 내린 의미가 없어짐 |
| **전부 취소된 행사** | 목록에 뜨면 취소 이력을 공개하는 것과 같음 (`04`). 일부 회차만 취소된 행사는 그대로 |

> 처음 보는 작은 극단이 믿을 만한지, 지난 공연이 있는지로 판단합니다 (`15` 한서윤).
> 지난 공연을 한 페이지로 보여줄 수 있어 극단 소개가 됩니다 (`15` 박정훈).

**운영진 프로필**

```
조용한고래
극단에서 연출하고 있습니다
──────────────
참여한 주최자
극단 열두달 · 소유자 · 2019~
늦여름 · 운영자 · 2023~2024 (활동 종료)
```

| | |
|---|---|
| 누구에게 | **운영진(소유자·운영자)만.** 운영진이 되면 자동으로 생김 |
| 보이는 것 | **닉네임 · 한 줄 소개 · 참여한 주최자 (이름 · 역할 · 기간)** |
| 보이지 않는 것 | 실명 · 이메일 · **관객으로서 예매한 내역** (같은 이메일로 관객 계정이 있어도 연결하지 않음) |
| 표시 | **사진은 받지 않습니다.** 닉네임 첫 글자 + 사람마다 정해진 색(주최자 로고와 같은 8가지). 얼굴이 공개 페이지에 남지 않게 |
| 지난 소속 | 나왔거나 닫힌 주최자도 이력으로 남음. 그 주최자의 정산·현황은 볼 수 없음 |
| 영구 정지된 주최자 | 페이지가 내려가고 프로필 목록에서도 빠짐 |

**관객 · 관리자 · 검표 계정에는 프로필이 없습니다.** 남이 그 사람을 볼 일이 없기 때문입니다. 현장 아르바이트는 운영진이 아니라 검표 계정을 씁니다.

> 정훈이 열두달을 6년 운영하다 새 프로젝트 팀을 만들어 첫 공연을 엽니다. 새 팀은 지난 공연이 없지만, 대표 프로필의 "극단 열두달 · 소유자 · 2019~"가 관객에게 믿을 근거가 됩니다 (`15` 박정훈).

**실명 대신 닉네임**이라 자동으로 공개해도 개인을 특정하지 않습니다. 그래서 공개 여부를 따로 묻지 않습니다.

**주최자명을 소유자가 바로 바꿀 수 있게 한 이유** — 이름을 바꾸는 일은 드물고, 관리자는 이름이 적절한지 미리 판단할 근거가 없습니다. 대신 사후 장치를 둡니다.

- **이름 변경 이력** — 행사는 주최자를 가리키기만 하므로 이름을 바꾸면 지난 행사 페이지에도 새 이름이 뜹니다. 행사 페이지는 표시·광고라 "샀을 때 무슨 이름이었나"를 확인할 근거로 남깁니다. 제목·소개·포스터 변경 이력과 같은 이유입니다 (`03` 참조)
- **관리자 알림** — 유명한 단체와 헷갈리게 하는 이름으로 바꾸면 관리자가 바로 알고, 신고·정지로 처리합니다

### 사용자

| 항목 | 쓰는 곳 | |
|---|---|---|
| 이름 | 검표 수동 검색 | 직접 입력 |
| 생년월일 | 연령 제한 · 만 14세 미만 차단 · **연령대 통계 (집계)** | 직접 입력 |
| 이메일 | 로그인 · 알림 | 직접 입력 + **인증** |
| 전화번호 | 검표 수동 검색 · 문자 알림 · **한 사람 구분** | 직접 입력 (**인증 없음**, 번호 하나에 계정 하나) |

**전부 필수이고, 이 넷 외에는 받지 않습니다.** 정보 항목에는 선택 항목을 두지 않습니다. (마케팅 수신 동의는 정보가 아니라 동의 항목이라 별개입니다. 아래 참조)

### 주최자 운영진

이름 · **닉네임** · 이메일(**인증**) · 비밀번호만 받습니다. 주최자의 연락처와 정산 계좌는 사람이 아니라 주최자 신청서에 붙습니다 (아래 참조).

| 닉네임 | |
|---|---|
| 입력 | 운영진 로그인을 만들 때 **필수.** **[랜덤 생성]** 버튼 (예: 조용한고래, 푸른바람) |
| 중복 | **불가.** 공개 프로필이라 같은 닉네임이 둘이면 구분되지 않음 |
| 변경 | 가능. 참여 이력은 그대로 따라감 |
| 부적절하면 | 관리자가 초기화 (닉네임 · 소개 모두) |

**관객에게는 닉네임을 받지 않습니다.** 관객 정보는 어디에도 공개되지 않아 쓸 곳이 없고, 가입 칸만 늘어납니다.

**성별은 받지 않습니다.** 예매에 쓰이지 않고 통계에만 쓰이는데, 그런 정보는 법상 필수로 받을 수 없고 (개인정보보호법 제16조), 선택으로 받으면 미응답이 섞여 통계가 흐려집니다. 연령대 통계만으로 충분하다고 판단했습니다.

**생년월일의 이용 목적에 "통계(집계)"를 적어둡니다.** 연령 제한 때문에 필수로 받는 정보지만, 주최자 통계에도 쓰이므로 가입할 때 보여주는 수집·이용 목적에 포함해야 합니다 (`11` 참조).

### 본인확인은 하지 않습니다

휴대폰 본인확인은 본인확인기관과의 계약이 필요해 테스트 결제 환경과 맞지 않습니다. 그래서 이름·생년월일·전화번호는 **본인이 직접 입력한 값이고 검증되지 않습니다.** 이 한계는 연령 제한(`03`), 매수 제한(`06`), 통계(`11`)에 각각 적혀 있습니다.

### 전화번호 — 인증하지 않고, 본인 번호라고 가정합니다

> **관객은 본인 전화번호를 정확히 적는다고 가정합니다.**

문자 인증번호도 받지 않습니다. 건마다 비용이 들고, 가입을 한 단계 늘립니다. 대신 이 전제 위에서 **번호 하나에 계정 하나**만 허용합니다.

| 규칙 | |
|---|---|
| 가입 | 같은 번호로 가입한 계정이 있으면 **가입 불가** |
| 번호 변경 (마이페이지) | 같은 확인. 다른 계정이 쓰는 번호로는 바꿀 수 없음 |
| 일반 탈퇴 | 번호가 풀려 다시 가입할 수 있음 |
| **이용 정지된 계정의 탈퇴** | 번호가 **차단 목록에 남아** 그 번호로 다시 가입할 수 없음 (아래 "관객 이용 정지") |

> 이미 가입된 번호입니다.
> 본인 번호가 맞다면 문의해 주세요.

**번호 하나가 곧 한 사람**이므로 1인 매수 제한(`06`)과 관객 이용 정지가 사실상 사람 단위로 걸립니다.

**감수하는 것 둘**

- **일부러 다른 번호를 적으면 뚫립니다.** 전제 밖의 일입니다
- **오타로 남의 번호를 적으면 그 번호의 진짜 주인이 가입하지 못합니다.** 인증이 없어 누가 진짜 주인인지 가릴 수 없으므로 문의로 개별 처리합니다

> 처음에는 번호를 받기만 하고 중복은 보지 않았습니다. 문자 인증을 붙여 확실히 막는 안도 검토했으나 비용 때문에 빼고, "본인 번호를 적는다"는 전제 아래 중복 확인만 두었습니다.

**만 14세 미만은 가입이 차단됩니다.** 생년월일로 걸러지고, 동의 항목에도 "만 14세 이상입니다"를 둡니다.

> 개인정보보호법 제22조의2는 만 14세 미만 아동의 개인정보 처리에 법정대리인 동의를 요구합니다. 가이드라인은 연령 허위 기재를 막을 **합리적 장치**를 권장하며, 그런 장치를 두었는데도 아동이 가입한 경우는 기망 동의로 보아 사업자 책임이 면제될 수 있습니다. **생년월일 차단과 동의 항목을 함께 두는 이유**가 이것입니다.

## 가입 경로

- **직접 가입** — 이메일 + 비밀번호, 이메일 인증
- **OAuth** — 구글·카카오 등

**OAuth로 가입해도 빠진 항목은 추가로 입력받습니다.** 구글은 이름과 이메일만 주고 생년월일·전화번호는 안 주므로, 실제로는 거의 모든 OAuth 가입자가 추가 입력 화면을 봅니다.

### OAuth는 중복 계정을 막지 못합니다

구글 계정은 누구나 여러 개 만들 수 있습니다. **OAuth는 편의 기능이지 본인확인이 아닙니다.**

그래서 OAuth로 가입해도 **전화번호 중복 확인을 똑같이 거칩니다** (위 참조). 구글 계정이 셋이어도 번호가 하나면 계정은 하나입니다.

### 계정 연동

**이메일이 같다고 자동으로 묶으면 안 됩니다.** 공격자가 피해자의 이메일로 OAuth 가입을 시도하면 기존 계정에 접근하게 됩니다.

**연동은 이미 로그인한 상태에서 사용자가 직접** 합니다.

> 이 이메일로 가입된 계정이 있습니다. 기존 계정으로 로그인한 뒤 구글 계정을 연결해 주세요.

## 같은 이메일로 양쪽 가입

한 이메일로 사용자 계정과 주최자 쪽 로그인을 둘 다 만들 수 있습니다. 소규모 공연판에서는 주최자들이 서로의 관객이기 때문입니다.

**주최자 쪽 로그인으로는 예매할 수 없습니다.**

- **로그인** — 일반 로그인 폼 아래에 "주최자 로그인" 링크
- **비밀번호 찾기** — 계정이 둘일 수 있으니 어느 쪽인지 물어야 합니다. **가입 여부와 상관없이 같은 안내**("입력한 이메일로 안내를 보냈습니다")를 보냅니다. 답이 다르면 이메일을 넣어 보며 가입자를 알아낼 수 있습니다
- **알림 메일** — 주최자 쪽 제목에 `[주최]` 접두사

## 약관과 동의

### 가입 시

| 항목 | |
|---|---|
| 서비스 이용약관 | 필수 |
| 개인정보 수집·이용 동의 | 필수 |
| 만 14세 이상 확인 | 필수 |
| 마케팅 수신 동의 | 선택 (**언제든 철회 가능.** 마이페이지에서 변경) |

**"필수 항목 모두 동의" 체크박스를 하나 둡니다.** 필수 셋만 한 번에 체크되고, 마케팅 수신은 여기에 묶지 않고 따로 고릅니다. 서두르다 원치 않는 광고 동의를 하지 않게 하려는 것입니다 (`15` 한서윤 — 광고성 연락을 원하지 않음). 각 항목은 그대로 펼쳐 보여줍니다.

**마케팅 수신 동의는 실제로 씁니다.** 관리자가 동의한 사람에게 신규 행사 소식을 이메일로 보냅니다 (`12` 참조). 받아두기만 하고 보내지 않으면 체크박스와 설정 스위치가 아무 일도 하지 않게 됩니다.

### 예매 시

| 항목 | |
|---|---|
| 취소·환불 규정 확인 | 필수 |
| 연령 제한 확인 | 해당 행사만 |
| 시야제한석 확인 | 해당 좌석만 |
| 휠체어석 확인 | 해당 좌석만 |

**예매 시 동의는 묶지 않고 하나씩 체크합니다.** 해당하는 항목은 모두 필수이고, 시야제한석처럼 분쟁 때 "고지했다"는 근거가 되는 것들이라 각각 확인받습니다 (`02` 참조).

### 주최자에게 개인정보를 넘기지 않습니다

그래서 **"주최자에게 예매자 정보 제공 동의"를 받지 않습니다.**

| 주최자 쪽이 보는 것 | |
|---|---|
| 예매자 명단 | 없음 |
| 이름 · 전화번호 · 생년월일 | 없음. 검표 결과에도 **티켓 정보(좌석·구역·회차)만** 나옴 (`10` 참조) |
| 판매 · 입장 현황 | 숫자 |
| 연령대 통계 | 예매자 30명 이상일 때 비율만 (`11` 참조) |

관객에게 보내는 알림은 우리가 발송합니다. 주최자가 관객에게 직접 연락할 경로는 없습니다.

> 처음에는 이름과 연락처를 주최자에게 넘기는 전제로 제공 동의를 필수로 받았으나, 명단·검표 결과에서 개인정보를 모두 걷어내 넘길 것이 없어졌습니다. 제3자 제공 동의는 실제로 넘길 때만 받는 것이라 이 구조에서는 필요 없습니다 (`99` A-5).

문서 내용 작성은 법률 검토 영역이라 기획 범위 밖입니다. **필요하다는 것과 어디에 붙는지만** 정해둡니다.

## 주최자 신청과 승인

```
주최자 쪽 로그인을 만든 뒤 신청서 제출
  → 플랫폼 관리자 검토 (영업일 3일 이내)
  → 승인 / 반려(사유 포함)
  → 승인되면 신청한 사람이 소유자가 되고 행사 개설 가능
```

승인 전까지 로그인하면 **"심사 중" 화면**만 보입니다. 어느 주최자에도 소속되지 않은 로그인은 "새 주최자 신청"과 "받은 초대"만 보입니다. 닫힌 주최자의 소유자였다면 "다시 열기 신청"도 보입니다.

**심사는 주최자 단위로 한 번입니다.** 나중에 들어오는 운영자는 심사하지 않습니다.

### 닫힌 주최자를 다시 열 때 — 이력은 이어집니다

**새 주최자로 신청하지 않고, 그 주최자를 다시 여는 신청**을 합니다 (GitHub의 보관된 조직을 다시 여는 것과 같음). 심사는 다시 받고, 행사·취소·정지 이력은 그대로 이어집니다.

> 취소를 여러 번 한 주최자가 닫고 같은 이름으로 새로 신청하면, 이력이 하나도 없는 새 주최자가 됩니다.

이런 **이력 세탁을 막으려고**, 새 신청이 들어오면 심사 화면에 **같은 소유자 또는 같은 단체명의 닫힌 주최자**를 함께 보여줍니다. 같은 단체로 보이면 관리자가 "다시 열기"로 돌립니다.

### 심사로 거르려는 것

> **실재하지 않거나 연락이 닿지 않는 주최자**

이것만 걸러도 대부분의 사고가 막힙니다. "좋은 공연인가"를 판단하려 들면 심사가 불가능해집니다.

## 통신판매중개자 의무

표를 파는 건 주최자이고, 우리는 판을 깔아줍니다. 전자상거래법상 **통신판매중개자**라 아래 세 가지를 지켜야 합니다 (`99` A-7).

### 1. "판매 당사자가 아니다"를 미리 알립니다

> [서비스명]은 통신판매중개자로서 통신판매의 당사자가 아닙니다. 행사의 내용과 진행에 대한 책임은 주최자에게 있습니다.

| 어디에 | |
|---|---|
| 모든 페이지 하단 | 운영자 정보와 함께 (아래 3) |
| 결제 화면 | 결제 버튼 위 한 줄 |
| 이용약관 | 조항으로 |

**미리 알리지 않으면 주최자 잘못으로 생긴 손해를 우리가 주최자와 같이 물어줘야 합니다.** 환불과 배상은 지금처럼 우리가 처리하고 주최자 정산에서 뺍니다 (`08` `11`). 이 고지가 그 흐름을 바꾸지는 않습니다.

### 2. 판매자 정보 — 사업자는 공개, 비사업자는 확인만

| | 사업자 | 비사업자 (개인 · 동아리 · 동호회) |
|---|---|---|
| 행사 페이지 "판매자 정보" | **상호 · 대표자 · 사업장 주소 · 사업장 전화번호 · 사업자등록번호** | 주최자명 + "비사업자 주최자입니다. 분쟁이 생기면 분쟁조정기구·법원의 요청이나 주최자 동의를 받아 연락처를 제공합니다" |
| 우리가 확인해 두는 것 | 위 항목 (심사 때) | 이름 또는 단체명 · 담당자 연락처 (심사 때 실제로 전화해봄) |
| 분쟁이 생기면 | 이미 공개돼 있음 | **관리자가** 분쟁조정기구·법원의 요청이 있거나 주최자가 동의한 경우 관객에게 제공 |

**사업자 주최자는 예매 전에 관객이 신원정보를 볼 수 있어야 합니다.** 그래서 행사 상세 하단에 둡니다. 사업장 전화번호는 항상 나옵니다. 행사 설정의 "공개용 연락처"(선택)와는 별개입니다.

**사업자 정보 수정은 관리자 확인 뒤 적용**합니다. 정산 계좌와 같습니다. 관객에게 보여준 신원정보가 사실과 다르면 우리가 같이 배상해야 합니다.

### 3. 우리 운영자 정보 — 모든 페이지 하단

상호 · 대표자 · 주소 · 전화번호 · 이메일 · 사업자등록번호 · 통신판매업 신고번호 · 호스팅 제공자 · **이용약관 · 개인정보처리방침 링크.**

테스트 운영 중에는 자리만 두고, 값은 실제 오픈 전에 채웁니다.

## 정지 4단계

| 단계 | 효과 | 쓰는 상황 |
|---|---|---|
| **1. 신규 개설 차단** | 새 행사 만들기 + 작성 중 행사의 판매 시작 차단. 이미 판매 대기·판매 중인 행사는 그대로 | 경고성, 미수금 장기 미납 |
| **2. + 판매 중단** | **관리자가 고른 행사**의 판매 중단. 기존 예매는 유지 | **의심스럽지만 확정 안 됨** |
| **3. + 전원 환불** | **관리자가 고른 행사**의 남은 회차 전부 취소 | 사기가 명백함 |
| **4. 영구 정지** | 남은 회차 전부 3단계 처리 + 주최자 폐쇄 + **소유자 개인 차단**. 정산 대기금은 보류 | 중대 위반 |

**2단계가 제일 자주 쓰일 겁니다.** 신고가 들어왔는데 확인이 안 됐을 때 추가 피해만 막고 조사합니다. 두 단계만 두면 관리자가 "아직 확실치 않은데 수백 명을 환불시켜야 하나"에서 멈춰버립니다.

### 정지는 주최자에, 판매 중단·취소는 고른 행사에

**정지 기록은 주최자에 걸립니다.** 운영진 전원이 영향을 받고, 심사·이력도 주최자 단위입니다.

**2·3단계의 판매 중단과 취소는 관리자가 대상 행사를 고릅니다.** 기본값은 진행 중인 행사 전부 선택입니다.

> 낭독회 하나가 문제인데 같은 주최자의 정기공연까지 멈추면 극단에 치명적입니다 (`15` 박정훈).
> 반대로 사기가 의심되면 관리자가 전부 고른 그대로 둡니다.

**3단계 실행 시** 고른 행사의 남은 회차가 전부 취소되고 전액 환불(공제 없음), 전원 통지, 10% 배상입니다 (`08` 참조). 이미 공연한 회차는 원래 정산 대상이지만, **공연이 실제로 열리지 않았다면** 관리자가 "지난 회차도 환불"을 고를 수 있습니다. 사기 행사는 날짜만 지났지 공연이 없었을 수 있기 때문입니다.

> ⚠️ 행사 2개, 예매자 312명이 전원 환불되고 남은 회차가 취소됩니다. 되돌릴 수 없습니다.
> ☐ 지난 회차도 환불 (공연이 열리지 않은 경우)

### 관리자가 멈춘 판매는 주최자가 풀 수 없습니다

| 시점 | 주최자의 [재개] |
|---|---|
| 정지 중 · 페이지가 내려간 동안 | **누를 수 없음.** "관리자 조치로 중단됨" 표시 |
| 해제된 뒤 · 페이지가 다시 올라간 뒤 | 누를 수 있음. 알림: "판매를 재개할 수 있습니다" |

**해제해도 판매는 저절로 열리지 않습니다.** 관리자가 멈추기 전에 주최자가 이미 판매를 멈춰 뒀을 수 있습니다. 저절로 열면 주최자가 닫아둔 판매가 모르는 사이 열립니다. 열지 말지는 주최자가 정하고, 알림 덕분에 버튼 한 번이면 됩니다.

**4단계는 주최자와 그 소유자 개인 둘 다에 겁니다.** 정지를 주최자에만 걸면, 소유자였던 사람이 다른 주최자에 운영자로 초대받아 그대로 활동할 수 있기 때문입니다.

- 차단된 사람은 **새 주최자 신청도, 다른 주최자의 운영자 초대 수락도** 할 수 없습니다
- 그 주최자의 운영자들은 그 주최자에서만 빠지고, 다른 주최자 활동은 그대로 합니다
- 가담한 운영자가 있으면 관리자가 따로 차단합니다
- **주최자 페이지를 내리고**, 운영진 프로필의 참여 목록에서도 빠집니다

**재가입 차단은 관리자가 차단 목록(이름·연락처)을 보고 수동으로 거릅니다.** 신청은 심사에 사람이 끼어 있어 대조할 수 있습니다. 운영자 초대 수락은 심사가 없어서 **같은 이메일만 자동으로 막히고, 새 이메일을 쓰면 막을 수 없습니다.** 본인확인을 하지 않는 구조의 한계입니다.

**정지 사유는 기록하고 주최자에게 통지**합니다. **해제 가능**하되 3단계로 이미 환불이 나갔으면 되돌릴 수 없습니다.

심사와 운영을 더 나누지는 않습니다. 1만 명 이하 규모에서 "심사만 하는 인력"이 따로 있을 가능성이 낮아, 등급을 늘리면 쓸 사람 없는 기능이 됩니다.

**모든 조작에 "누가 언제 무엇을"을 기록**합니다. 되돌릴 수 없는 조작을 추적하려면 필요합니다.

## 검표 계정

**개인의 계정이 아니라 입구에 놓인 태블릿에 가깝습니다.** 이메일도 개인정보도 비밀번호 찾기도 없습니다.

| 항목 | 결정 |
|---|---|
| 발급 단위 | **행사당 1개** |
| 로그인 | ID + 비밀번호 |
| 볼 수 있는 것 | 검표 화면만 |
| 입구 구분 | 로그인 후 기기에서 선택, **중간 변경 가능** |
| 동시 로그인 | **허용** |
| 수명 | **마지막 회차 종료 시 잠김** |
| 비밀번호 분실 | 운영진이 재발급 (기존 로그인 전부 끊김) |
| 예매자 명단 | **열람 불가** (주최자도 마찬가지, `10` 참조) |

**동시 로그인 허용이 전제입니다.** 입구가 3개면 태블릿 3대가 같은 계정으로 로그인해 각자 다른 입구를 고릅니다. **입구 선택은 기기별로 따로 유지**됩니다.

운영진 로그인과 분리한 이유는 단순합니다. 스태프가 아르바이트일 수 있는데, 운영진 로그인으로는 매출·환불·행사 설정까지 전부 열립니다.

**공연 당일에 비밀번호를 재발급하면** 로그인된 태블릿이 전부 끊기므로 경고를 띄웁니다.

## 신고

**관객이 행사를 신고**합니다. 허위 정보, 부적절한 내용, 사기 의심, **공연 지연, 출연자 변경**.

**로그인이 필요합니다.** 버튼은 행사 상세에 누구나 보이게 두고, 누르면 로그인합니다. 익명으로 받으면 같은 사람이 수십 번 신고해도 가릴 수 없습니다.

사유 선택지 + 자유 기술을 받고, 관리자가 검토합니다.

| 누구에게 | 무엇을 |
|---|---|
| **신고자** | 접수 확인 + **처리 결과 한 줄** ("조치했습니다" / "문제를 찾지 못했습니다"). 이메일. 조치 내용은 알리지 않음 |
| **주최자** | **접수 사실은 알리지 않음.** 관리자가 조치할 때만 알림 |

**주최자에게 접수를 알리지 않는 이유** — 악의적인 신고까지 전부 주최자에게 가면, 관리자가 걸러내기 전부터 주최자가 시달립니다 (`15` 박정훈).

**공연 지연·출연자 변경 신고**는 주최자가 처리하지 않은 경우입니다. 관리자가 주최자에게 확인한 뒤 **주최자 대신 같은 처리**를 합니다 (`08` 참조).

### 관리자가 쓰는 조치는 문제의 종류로 갈립니다

```
신고 접수 → 관리자 확인
 ├─ 내용만 문제 (개인정보 노출, 부적절한 문구)
 │   ├─ 판매 중: 주최자에게 수정 요청. 안 고치면 페이지 내리기
 │   └─ 판매 종료 후: 주최자가 고칠 수 없으므로 바로 페이지 내리기
 ├─ 공연 지연 · 출연자 변경을 주최자가 처리하지 않음
 │   → 관리자가 대신 처리 (`08` 참조)
 └─ 행사 자체가 문제 (사기, 허위)
     → 정지 단계 (판매 중단 → 전원 환불)
```

### 수정 요청

| | |
|---|---|
| 수단 | 이메일 + 주최 관리의 그 행사 화면 상단에 안내 (요청 내용 · 기한) |
| 기한 | **기본 3일**, 관리자가 정함. 개인정보 노출처럼 급하면 요청 없이 바로 내림 |
| 주최자 | 고친 뒤 **[수정 완료]** → 관리자가 확인하고 종료 |
| 기한을 넘기면 | 관리자가 페이지 내리기 |

### 행사 페이지 내리기

**계정 정지와 별개로, 행사 하나의 페이지만 숨기는 조치**입니다.

판매가 끝나면 주최자는 제목·소개·포스터를 고칠 수 없고 (`04` 참조), 표가 팔린 행사는 지울 수도 없습니다. 그 상태에서 내용에 문제가 생기면 막을 수 있는 사람이 관리자뿐입니다. 페이지 하나 때문에 계정을 정지하는 건 과합니다.

| | |
|---|---|
| 하는 사람 | **관리자만.** 주최자는 문의 창구로 요청 |
| 페이지 | 링크를 열면 "운영 정책에 따라 비공개 처리된 행사입니다" |
| 판매 | 판매 중이었다면 판매 중단 (페이지 없이는 예매 불가). **주최자가 재개할 수 없음** |
| 다시 올리기 | **관리자만.** 다시 올린 뒤 판매 재개는 주최자가 함 (위 "관리자가 멈춘 판매" 참조) |
| **산 표** | **그대로 유효. 환불하지 않음.** 공연도 그대로 진행 |
| 예매 카드 · 결제 기록 | 그대로 |
| 통지 | 공연 전이면 산 사람에게 "예매는 그대로 유효합니다" (`12` 참조) |

**환불하지 않는 이유** — 페이지 내리기는 내용 문제를 다루는 조치이고, 공연 자체는 멀쩡합니다. 소개글에 연락처 하나 잘못 적었다고 300명이 환불되면 안 됩니다. 행사 자체가 문제라면 정지 단계를 씁니다.

**주최자가 직접 내릴 수 없는 이유** — 끝난 행사 페이지를 남기는 건 공유된 링크가 깨지지 않게 하기 위해서입니다 (`04` 참조). 주최자가 마음대로 내릴 수 있으면 그 원칙이 무너집니다.

## 문의 창구

**관객 → 주최자** — 주최자가 행사 설정에 **공개용 연락처를 선택 입력**합니다. 적으면 행사 페이지에 표시됩니다.

서비스 내 메시지 기능은 만들지 않습니다. 메시지함, 알림, 스팸 처리까지 따라옵니다.

**관객 → 플랫폼** — 문의 이메일 주소 하나.

**주최자 → 플랫폼** — 같은 문의 이메일. 매수 제한을 넘는 다중 예매처럼 관객 쪽 문제를 알릴 때도 씁니다.

## 관객 이용 정지

**관객 계정에 거는 제재는 하나뿐입니다.**

| | |
|---|---|
| 막히는 것 | **새 예매 · 변경 · 신고** |
| 되는 것 | 로그인, 기존 티켓 보기 · QR · 취소 (**산 표는 뺏지 않음**) |
| 누가 | 관리자 |
| 기록 · 통지 | 사유 기록, 이메일 통지 |
| 해제 | 가능 |
| 탈퇴하면 | 그 번호는 **차단 목록에 남아** 다시 가입할 수 없음 |

**쓰는 경우** — 번호를 바꿔가며 매수 제한을 넘는 예매, 반복되는 허위 신고 같은 것입니다.

**번호 하나에 계정 하나**이므로 같은 번호로 새 계정을 만들어 피할 수 없습니다 (위 "전화번호" 참조).

### 전매 의심 표를 강제 취소하지는 않습니다

> 중고거래 사이트에 "3일권 15만원에 팝니다"와 QR 캡처가 올라왔습니다.

이 표를 취소하는 기능은 만들지 않습니다.

- **공유와 전매를 구분할 수 없습니다.** 친구에게 QR을 보내는 건 정상 기능이고, 돈을 받았는지는 기록에 없습니다
- **피해가 엉뚱한 사람에게 갑니다.** 취소할 즈음이면 이미 팔린 뒤라, 돈을 낸 구매자가 현장에서 막히고 판 사람은 돈을 이미 받았습니다

팔린 표를 뒤쫓는 대신 **애초에 많이 못 사게** 막습니다 — 번호 기준 매수 제한(`06`)과 이용 정지.

## 탈퇴와 주최자 닫기

| | 언제 가능한가 |
|---|---|
| **운영자** 탈퇴 | 언제든. 소속 주최자에서 빠짐 |
| **소유자** 탈퇴 | 먼저 소유자를 넘기거나 주최자를 닫아야 함 |
| **주최자 닫기** (소유자만) | **정산이 끝나지 않은 행사가 하나도 없고, 미수금이 없을 때** |
| **사용자** 탈퇴 | **공연 전 티켓이 없을 때** |

공연이 끝났어도 환불 가능 기간이 남아 있고 정산도 안 됐다면 주최자가 사라지면 처리할 사람이 없습니다. 정산 완료가 "이 행사는 끝났다"의 기준입니다. 취소된 행사도 정산을 거칩니다 (`11` 참조).

> 진행 중이거나 정산이 완료되지 않은 행사가 있습니다.
> 모든 행사를 마무리한 뒤 닫을 수 있습니다.

**닫은 뒤에는** — 주최자는 사라지지 않고 **"닫힘" 상태로 남습니다.**

| | |
|---|---|
| 운영진 | 전원 그 주최자에서 빠짐. 프로필에는 "활동 종료"로 이력이 남음 |
| 새 행사 | 열 수 없음 |
| 주최자 페이지 · 지난 행사 페이지 | **그대로 남음.** "활동 종료" 배지. 공유된 링크가 깨지지 않게 한다는 원칙(`04`)은 주최자가 닫혀도 같음 |
| 검표 계정 | 이미 마지막 회차 종료 때 잠김 |
| 이력 (행사·취소·정지·정산) | 그대로 보존. 관리자가 봄 |
| 다시 열기 | 그 주최자를 다시 여는 신청 → 심사 (위 "닫힌 주최자를 다시 열 때") |

**사용자 탈퇴는 공연 전 티켓이 있으면 막습니다.**

> 공연 전 티켓이 3장 있습니다.
> 티켓을 취소하거나, 공연이 끝난 뒤 탈퇴할 수 있습니다.

자동으로 취소하면 공제로 돈을 잃고, 티켓을 남겨두면 QR을 볼 계정이 사라집니다. 서비스를 정리하다 남은 표를 잊는 일은 흔합니다 (`15` 한서윤).

**사용자 탈퇴 시**에는 법정 보존 대상(결제 기록)만 남기고 개인 식별 정보를 분리합니다 (`11` 참조). 전화번호는 풀려 다시 가입할 수 있습니다. 이용 정지된 계정은 예외입니다 (위 참조).

## 화면 공간 분리

- **마이페이지** = 관객으로서의 나 → 예매 내역, 티켓, 변경·취소, 알림 설정, 계정 정보
- **주최 관리** = 주최자 운영진으로서의 나 → 행사 목록, 좌석 배치, 판매 현황, 검표 계정, 정산, 운영진 관리, 주최자 전환 (여러 곳에 소속된 경우)

한 곳에 넣으면 예매를 취소하러 들어온 사람이 매출 그래프부터 보게 됩니다.
