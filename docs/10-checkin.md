# 10. 검표

QR과 티켓의 구조는 `07`에 있습니다. 이 문서는 **현장에서 벌어지는 일**을 다룹니다.

## 검표 화면

스캔 성공 시 **크게** 표시할 것:

```
✓ 유효

1층 12열 7번
━━━━━━━━━━━━━
R석 · 3/14 19:00
```

**좌석만 크게, 나머지는 작게.** 스태프가 보는 건 "통과시켜도 되나"와 "어디로 안내하나" 둘뿐입니다.

**이름은 띄우지 않습니다.** 입장은 티켓으로 처리하고 이름은 대조하지 않으므로 (아래 참조) 쓸 데가 없습니다. 검표 화면에 개인정보가 하나도 나오지 않으니, 주최자 쪽 스태프에게 넘어가는 개인정보도 없습니다 (`01` 참조).

**수량형은 구역과 티켓 번호**입니다 (`07` 참조).

```
스탠딩A · 0091-2
```

**묶음권은 그 날의 회차가 붙습니다.**

```
스탠딩A · 5/4 입장분
3일권 (5/3~5/5) · 2일차
```

시간대를 나눈 행사라면 회차까지 나옵니다.

```
스탠딩A · 5/4 14-16시 입장분
3일권 (5/3~5/5) · 2일차
```

## 같은 화면에 반드시 있어야 할 것

- **수동 검색** — 아래 참조. **실무에서 제일 자주 쓰는 기능**
- **입구 선택** — 로그인 후 고르고, **중간에 바꿀 수 있습니다**. 정문 줄이 길어지면 스태프가 2층으로 이동합니다. 바꾸기 전까지 찍은 건 이전 입구로 기록됩니다. **검표 계정은 행사당 하나이고 입구는 계정이 아니라 입장 기록에 적힙니다** — 기기 두 대가 각자 다른 입구를 골라도 서로 영향이 없습니다 (`14` 참조)
- **연령 제한 배지** — 청소년 관람불가 행사면 상단에 "신분증 확인" 고정 표시

**입장 누계는 검표 화면에 띄우지 않습니다.** 주최자 화면에서만 봅니다 (`11` 참조).

## 결과 화면 — 무엇이 뜨나

**스태프가 판단하지 않게, 모든 경우의 화면을 정해둡니다.** 애매한 화면이 뜨면 아르바이트생이 관객과 실랑이합니다 (`15` 이도현).

| 결과 | 화면 | 동작 |
|---|---|---|
| 정상 | ✓ 유효 + 좌석 크게 | 통과 |
| 이미 입장 | ⚠️ 최초 입장 시각·입구 | **경고.** [그래도 입장 처리] (아래) |
| 다른 날짜 · 다른 회차 | ❌ "이 티켓은 5월 15일 입장분입니다" | 차단 |
| 입장 시간 전 | ❌ "입장 가능: 18:00부터" | 차단 |
| 취소된 티켓 | ❌ "취소된 티켓입니다 · 회차 취소" (사유 표시. 사유가 "초대권 회수"면 "회수된 초대권입니다") | 차단 |
| 취소된 회차 | ❌ "취소된 회차입니다" (묶음권의 취소된 날) | 차단 |
| 환불받은 날짜 | ❌ "환불받은 날짜입니다" (묶음권에서 출연자 변경으로 포기한 날, `04`) | 차단 |
| 재발행 전 QR | ⚠️ "재발행으로 바뀐 QR입니다. 관객 폰에서 새 QR을 열거나 수동 검색하세요" (`07`) | 차단 |
| 다른 행사의 QR | ❌ "이 행사의 티켓이 아닙니다" | 차단 |
| 알 수 없는 QR | ❌ "확인할 수 없는 QR입니다. 수동 검색하세요" | 차단 |

**어느 화면에도 이름은 나오지 않습니다** (아래 "이름 대조는 하지 않습니다").

### 신호 — 화면이 기본, 소리는 보조

| | |
|---|---|
| 기본 | **화면 전체 색 + 아이콘 + 문장.** 어떤 기기에서도 동작. 색만으로 구분하지 않음 |
| 소리 | **기본 켬.** 통과·경고·차단이 서로 다른 소리. 기기마다 끌 수 있음 |
| 진동 | **지원하는 기기에서만** 함께. 아이폰 웹 브라우저는 진동을 쓸 수 없음 |

**소리를 기본으로 켜는 이유** — 입구에는 5분에 100명이 옵니다 (`15` 이도현). 스태프는 다음 관객을 보느라 화면만 보고 있을 수 없어서, "찍혔다"와 "막혔다"를 귀로 먼저 알아야 줄이 밀리지 않습니다. 객석 근처라 조용해야 하면 그 기기에서 끕니다.

## 수동 검색

관객 휴대폰이 꺼졌거나 QR이 안 읽힐 때 씁니다.

```
이름 + 연락처 뒷 4자리
 ├─ 한 사람 → 표시
 ├─ 여러 사람 → "같은 조건으로 찾은 분이 여러 명입니다. 전화번호 전체를 입력해 주세요"
 │              → 표시
 └─ 없음 → "찾지 못했습니다. 전화번호 전체로 다시 찾아볼까요?"
            → 표시
            → 그래도 없으면 현장 판단 (아래 참조)
```

**전화번호 전체 입력 칸은 첫 검색으로 못 찾았을 때만 나타납니다.**

**목록은 끝까지 안 보여줍니다.** "여러 명이다"는 사실만 알리고 추가 입력을 받습니다. 스태프는 화면이 시키는 대로만 하면 되고 판단할 게 없습니다.

**검표 스태프는 대개 아르바이트**입니다. "여러 명 나오면 알아서 더 물어보세요"라고 하면 사람마다 다르게 행동하고, 줄이 밀린 상황에서는 대충 넘길 수도 있습니다.

같은 이름이면서 연락처 뒷 4자리까지 같은 경우는 드물어 **평소 흐름은 첫 검색으로 끝납니다.**

**"한 사람"은 그 사람의 표 전부입니다.** 4장을 샀으면 4장이 나옵니다. 다른 사람 표가 섞이지 않으니 목록이 아닙니다. 스태프는 앞에 온 사람 수만큼 한 장씩 입장 처리합니다.

**생년월일은 묻지 않습니다.** 여러 명이 걸려도 전화번호 전체를 넣으면 한 사람으로 좁혀집니다. 번호 하나에 계정 하나이기 때문입니다 (`01` 참조). 생년월일은 검표에 쓰지 않습니다.

**예매번호로도 찾지 않습니다.** 폰이 꺼진 관객은 예매번호가 적힌 문자도 볼 수 없습니다.

**초대권도 같은 검색으로 찾힙니다.** 주최자가 발권할 때 받는 사람 이름과 연락처를 적은 경우입니다. 연락처가 없는 단체 초대는 담당자가 링크 페이지에서 그 사람의 QR을 보여주면 됩니다 (`09` 참조).

**수동 검색으로 들어가도 QR 스캔과 똑같이 입장 기록이 남습니다.** 검표 수단이 다를 뿐 결과는 같습니다.

### 이 흐름으로 풀리는 경우

| | 상황 | 어디서 풀리나 |
|---|---|---|
| ① | 가입할 때 이름을 다르게 적음 ("철수킴", 오타) | 첫 검색 "없음" → 전화번호 전체 |
| ② | 친구가 산 표를 공유받아 옴 | 친구에게 전화해 친구 이름과 번호로 찾음. 또는 친구가 링크를 다시 보내줌 |
| ③ | 초대권으로 옴 | 연락처가 있으면 같은 검색. 없으면 담당자 링크 페이지나 주최자의 초대권 목록 |
| ④ | 그 사이 전화번호를 바꿈 | **못 풂** → 현장 판단. 번호를 바꾼 데다 그날 폰까지 안 되는 경우라 드묾 |

### 떠보기 위험

"없음" 쪽에서는 이름과 상관없이 전화번호만으로 찾습니다. 아무 이름이나 넣고 넘어가면 전화번호만으로 검색할 수 있다는 뜻입니다. 그래도 문제는 작습니다.

- **11자리를 다 알아야 합니다.** 첫 검색(이름 + 뒷 4자리)보다 떠보기가 쉬워지지 않습니다
- **결과에 이름이 나오지 않습니다.** 티켓 정보(좌석·구역·회차)만 나오므로 번호로 이름을 알아내는 데 쓸 수 없습니다

### 그래도 못 찾으면 — 현장 판단

들여보낼지는 **주최자가 현장에서 정합니다.** 시스템이 더 해줄 수 있는 게 없습니다. 초대권이라면 주최자가 초대권 목록에서 확인합니다.

**검표 계정 화면에는 들여보내는 버튼이 없습니다.**

> ❌ 찾지 못했습니다.
> 현장 책임자를 불러주세요.

**[티켓 없이 입장 처리]는 운영진 로그인의 검표 화면에만** 있습니다. 판단은 주최자가 한다는 원칙을 화면 권한으로 지키는 것입니다. 아르바이트생은 고민할 필요 없이 책임자를 부르면 됩니다 (`15` 이도현).

```
[티켓 없이 입장 처리] (운영진)
  인원     [1] 명
  사유     ○ 폰이 꺼짐  ○ 조회되지 않음  ○ 기타 (직접 입력)
  입구     정문 (현재 선택된 입구)
```

| 기록 | |
|---|---|
| 붙는 곳 | **회차** (티켓이 없으므로) |
| 남는 것 | 시각 · 입구 · 인원 · 사유 · **누가 처리했는지** (운영진 이름) |
| 남지 않는 것 | **관객 이름** — 개인정보를 쌓지 않음 |
| 보관 | 입장 기록과 같이 **30일 후 삭제**, 숫자만 남음 |
| 입장 현황 | "티켓 없이 입장 N명"으로 **따로 셈** (`11` 참조) |

**운영진 이름을 남기는 이유** — 검표 계정은 공용이라 누가 눌렀는지 알 수 없습니다 (`01` 참조). 운영진 로그인은 개인 것이라 나중에 대표에게 "그때 왜 들여보냈나"를 설명할 근거가 됩니다.

### 예매자 명단은 누구도 보지 못합니다

| 계정 | 볼 수 있는 것 |
|---|---|
| 검표 계정 | 위 검색으로 찾은 표만 |
| 주최자 운영진 | **같음.** 별도 명단 화면도, 별도 검색도 없음. 다른 점은 **[티켓 없이 입장 처리]** 하나 |

주최자가 현장에 나와도 **같은 검표 화면, 같은 검색**을 씁니다. 주최자용 검색을 따로 둬도 쓸 수 있는 정보가 같아서, 스태프가 못 찾은 표를 주최자가 찾을 수는 없습니다.

주최자가 보는 건 예매 현황·입장 현황 같은 **숫자**와, 현장 검색으로 찾은 **표 한 장**뿐입니다.

> 처음에는 "검표 계정은 단건 조회, 주최자는 전체 명단 열람"이었고, 수동 검색은 "이름 + 뒷 4자리 → 겹치면 생년월일"이었습니다. 수동 검색에 전화번호 전체를 더하자 주최자가 명단을 훑어야 할 경우가 사라져 명단 화면을 없앴습니다.

## 검표 시작 시각

**회차 시작 1시간 전부터** 열립니다 (주최자 조정 가능, `03` 참조).

> ❌ 아직 입장 시간이 아닙니다
> 입장 가능: 18:00부터

**없으면 전날 미리 찍어서 입장 처리되는 사고**가 납니다.

## 중복 스캔 — 차단이 아니라 경고

현장에서 정당한 중복이 꽤 많습니다. 스캐너 오작동, 스태프가 두 번 찍음, 앞사람이 실수로 뒷사람 QR을 보여줌.

```
⚠️ 이미 입장 처리된 티켓
최초 입장: 19:04 / 정문
좌석: 12열 7번

[그래도 입장 처리]
```

**막지 않고, 판단 근거를 주고, 최종 결정은 사람이 합니다.** 강제 통과한 건은 기록에 남겨 주최자가 나중에 볼 수 있게 합니다.

**재입장이 켜져 있으면**(`03` 참조) 중복 스캔이 경고가 아니라 **"두 번째 입장"으로 기록**됩니다. 정상 통과입니다.

## 날짜가 틀리면 차단

묶음권 티켓을 그 티켓이 가리키지 않는 회차에 찍으면 **거부**합니다.

> ❌ 이 티켓은 **5월 15일** 입장분입니다
> 오늘은 5월 14일입니다

**경고가 아니라 차단**입니다. 중복 스캔은 정당한 경우가 많지만, 날짜가 틀린 건 정당한 경우가 없습니다. 안 그러면 3일권으로 첫날에 세 명이 들어갑니다.

## 이름 대조는 하지 않습니다

**QR 열쇠만으로 통과시킵니다** (`07` 참조). 이름은 화면에 뜨지도 않습니다.

**본인확인을 하지 않으므로 예매자 이름이 실명인지 확인할 방법이 없습니다** (`01` 참조). 대조할 근거가 애초에 없으니 대조하지 않는 게 일관됩니다.

**예외는 연령 제한 행사**입니다. 이때는 스태프가 신분증 실물을 확인합니다. 시스템이 아니라 현장 규칙이고, 우리가 할 수 있는 건 배지를 띄워 스태프가 잊지 않게 하는 것까지입니다.

**휠체어석도 현장에서 확인**됩니다. 공간 구조가 달라 일반 관객이 앉으면 바로 드러납니다 (`02` 참조).

## 네트워크가 끊기면

> **검표 현장은 전원과 인터넷이 있다고 가정합니다.**

**오프라인 검표는 만들지 않습니다.** 티켓 목록을 기기에 저장해두면 분실 시 그 자체가 개인정보 유출이고, 기기 두 대가 각자 오프라인이면 같은 QR을 둘 다 통과시킵니다.

### 관객에게 — QR 미리 저장 안내

예매 완료 직후와 전날 리마인더에 붙입니다 (`12` 참조).

> 💡 현장에서 인터넷이 불안정할 수 있습니다. **QR을 미리 캡처해두면** 안심할 수 있어요.

**캡처는 어차피 유효합니다.** QR에는 열쇠 하나만 들어 있고 검증은 스캐너 쪽에서 하니까요. 관객 폰이 안 터져도 스태프 기기만 연결되면 입장됩니다.

**QR을 재발행하면 옛 캡처는 무효**입니다. 그래서 재발행 완료 안내에 "저장해 둔 캡처도 새로 저장하세요"를 넣고, 옛 캡처를 찍으면 위조가 아니라 "재발행으로 바뀐 QR"로 알려줍니다 (`07` 참조).

**이게 제일 현실적인 대비입니다.** 관객 수백 명의 인터넷보다 스태프 기기 한두 대의 인터넷을 챙기는 게 훨씬 쉽습니다.

### 예매자 명단 내려받기는 만들지 않습니다

인터넷이 끊길 때를 대비해 주최자가 명단을 미리 받아두게 하는 안이 있었으나 **없앴습니다.** 드문 상황 하나를 대비하는 대가로 **수백 명의 이름·생년월일·연락처가 파일로 나갑니다.** 파일이 나간 뒤 어떻게 쓰이는지는 확인할 방법이 없습니다.

**화면에서 명단을 보는 기능도 없습니다.** 주최자를 포함해 누구도 전체 명단을 보지 못합니다 (위 "예매자 명단은 누구도 보지 못합니다" 참조).

> 처음에는 "권장 수단"으로 내려받기 모달·기록·파기 서약까지 두었으나, 개인정보를 파일로 내보내는 위험이 얻는 것보다 크다고 판단해 뺐습니다.

### 그래도 끊기면

현실적인 대응은 테더링, 신호 잡히는 곳으로 입구 이동, 일단 들여보내고 나중에 확인 정도입니다. **시스템이 해결할 문제가 아닙니다.**

## 퇴장 스캔은 없습니다

**현장 체류 인원 관리는 의도적으로 범위 밖입니다.** 정확히 알려면 퇴장 스캔이 필요한데, 입구에 줄이 생기고 실패율이 높습니다.

대신 간접적으로 대응합니다.

- 인원이 걱정되는 전시는 **회차형으로 등록해 시간대를 나눠** 입장 시점을 분산 (`02` 참조)
- 재입장이 기본 OFF이므로 **입장 누계가 곧 현재 인원의 근사치**
- 그 이상의 실시간 혼잡 관리는 현장 스태프의 눈

**정원은 판매 수량 상한이지 동시 체류 인원이 아닙니다.** 이 구분을 안내 문구에도 반영해야 합니다.

## 검표 기록 보관

입장은 티켓에 **기록으로 쌓입니다** (`07` 참조).

| | 30일 후 |
|---|---|
| 입장 기록 (회차·시각·입구·검표 수단·강제 통과) | **통째로 삭제** |
| 티켓 없는 입장 기록 | **통째로 삭제** |
| 게이트별·시간대별 집계 숫자 | **유지** |
| 티켓 (좌석·금액·취소 여부) | **유지** — 5년 법정 보존 (`07`, `11` 참조) |

**30일은 행사가 끝난 날부터** 셉니다 (`04` 참조).

**30일이 필요한 이유** — 행사 직후에 분쟁이 가장 많이 나옵니다. "저 들어갔는데 안 들어갔다고 하네요"에 답하려면 시각과 입구가 필요합니다. 30일이면 정산과 분쟁 제기가 대부분 끝납니다.

**지우는 이유는 용량이 아니라 개인정보입니다.** "이 사람이 5월 3일 10시 12분에 정문으로 들어왔다"는 **개인 동선**입니다. 목적을 달성한 뒤에는 파기합니다.

반면 티켓은 "12열 7번을 5만원에 공급했다"는 **거래 기록**이라 법이 남기라고 합니다. 성격이 다릅니다.

**티켓에 "입장했음" 같은 요약도 남기지 않습니다.** 주최자의 입장률은 집계 숫자로 남고, 1년 전 공연에 "입장 완료"가 붙어 있을 필요가 관객에게 없습니다.
